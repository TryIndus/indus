# PostgreSQL event transport rollout

The cost-reduced runtime replaces the two active Kafka uses: report lifecycle delivery and market-data durability. It reuses Aurora and the existing Sidekiq worker. MSK Terraform and Kafka code remain in the repository. **A code merge or transport switch does not stop MSK billing; the provisioned cluster must be removed in a separately reviewed infrastructure change.**

Keep production on `EVENT_TRANSPORT=kafka` until the PostgreSQL market-data migration has run and the new Rails and Rust images are deployed. Back up Aurora and record the image digests, outbox backlog, Kafka consumer lag, and rollback point. The Rust service applies its additive SQL migration on startup. Verify `market_data.direct_event_journal` exists and the existing Kafka path still serves charts and reports before switching.

In a separate GitOps change, set `config.eventTransport: postgres` and `reportsConsumer.replicas: 0` together. Keep `platformOutbox.replicas: 1`. Check that both Rails and Rust pods report ready, report outbox rows gain `published_at`, report jobs complete, bars and quotes gain journal rows without Kafka offsets, and stock and crypto SSE streams update and reconnect. Check two market-data pods before allowing autoscaling above one. Monitor Aurora connections, CPU, storage, and query latency; direct journal polling moves work from MSK to Aurora.

Do not remove MSK until the old Kafka outbox and market consumer lag are drained, the direct path has survived restart and dependency recovery, and the cost/performance comparison is acceptable. Preserve the old images and broker endpoints through observation. Rolling back the GitOps setting to Kafka requires reconciling events written only to the PostgreSQL journal first; changing the flag alone would leave a market-data gap. If a safe reconciliation cannot be completed, keep direct mode active while repairing it.
